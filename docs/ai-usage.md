# AI の利用記録

課題は AI サービスの利用を認めており、「利用にあたって工夫したプロンプトやソースコメント等を
ご提出頂くことで、加点評価する場合もあります」と明記しています。この文書はその提出物です。

本プロジェクトは **Claude Code（Anthropic）** を主たる実装パートナーとして全面的に利用しています。
コードの大半は AI が書き、その全てを人間がレビューし、機械的なゲートを通してからマージしています。

---

## 1. 最も有効だった手法 — 規約をプロンプトではなく実行可能な統制として実装する

規約を AI に遵守させる手段として一般的なのは、プロンプトに規約を記述する方法です。ただし
これは有効に機能しません。会話が長くなるほど内容が希薄になり、遵守されなかった事実を
検知する手段も存在しないためです。

そこで、**AI に守らせたい規則はすべて、守らなかったときにビルドか CI が落ちる形**に置き換えました。

| 守らせたい規則 | それを強制しているもの |
|---|---|
| `:domain` は Ktor も Compose も `androidx` も知らない | モジュールの依存宣言（コンパイルが通らない） |
| DI グラフの束ね忘れがない | `checkModules()` のテスト |
| 公開 API を無自覚に増やさない | 全ライブラリモジュールで Explicit API mode `strict` |
| コンポーザブルに文字列をハードコードしない | 文字列は `:core:designsystem` の 1 バンドルのみ |
| 日本語訳のキー欠落を見逃さない | `verifyTranslations` タスク（`check` に接続） |
| prod の成果物がトークンを運べない | `build-logic` の 15 件のテスト（ルートの `check` に接続） |
| Android の APK がリソースを積んでいる | `verifyProdReleaseComposeResources`（後述の 3-1 の再発防止） |
| リダイレクト時に認証情報を漏らさない | `RedirectSecurityTest` |
| Ktor のバージョンアップで挙動が変わったら気付く | `MockEngine` によるレート制限・リトライ・タイムアウトのテスト |
| フォーマットとコードスメル | ktlint + detekt + Android Lint（CI ゲート） |
| このプロジェクト固有の欠陥 | `.coderabbit.yaml` の `path_instructions` |
| シークレットがリポジトリに入らない | `.gitignore` + ビルド時注入 + `PreToolUse` フック（後述、自己テスト 49 件） |

自然言語の指示として残っているのは、機械化できない部分（設計の意図、なぜこの版なのか）だけです。

### プロジェクト規約ファイル

リポジトリのルートに、エージェント向けのプロジェクト規約ファイルを置いています。770 行あり、
役割（KMP テックリードとして、あらゆる変更に対しセキュリティ / 正しさ / 性能 / 有効性の 4 点を
答えてから完了とする）、TDD の運用（Canon TDD の 5 手順、やってはいけない 8 パターン、
テストダブルは Fake 既定）、レイヤリング、DI、並行処理、Ktor、GitHub API の 3 つの罠、
セキュリティ、Compose のパフォーマンス、Kotlin のスタイル、エラーハンドリング、
Git 運用、そして「止まって聞くべき状況」の一覧で構成されています。

特に効果が確認できた項目は以下のとおりです。

- **「止まって聞く」ガードレールの表。** 「固定バージョンが解決しない場合、**近い数字で黙って
  代用しない** — 何が失敗したかを報告し、ADR として提案する」。これがないと、AI は
  `1.2.3` が無いときに `1.2.2` を入れて先に進み、「検証済み」と書かれた表が静かに腐ります。
- **「エージェントは履歴を書かない」。** `git commit` / `push` / `gh pr create` を実行させず、
  ブランチとコミットの計画を提出させて人間が実行します。コミット粒度は評価対象であり、
  そこは委譲すべきでない判断です。
- **「Duplication is a hint, not a command」（Kent Beck）。** 最初の重複で抽象化を行わせない
  規定です。制約がない場合、AI は 2 箇所目の出現時点で基底クラスを導入する傾向があります。
- **TDD の失敗パターン表。** 特に「テストを緑にするために表明を削る・弱める」「計算結果を
  期待値として貼り付ける」を明示的に禁止しています。後者は AI に生じやすい失敗であり、
  結果としてバグをアサートするテストが残ります。

この規約ファイルはリポジトリに含めています（[`CLAUDE.md`](../CLAUDE.md)）。下記のシークレット
保護フック（[`.claude/`](../.claude)）も同様です。本文書はその読み方の案内です。

### シークレット保護フック

規約に「シークレットを書くな」と書いても、それは検知できません。そこで `.claude/settings.json` の
`PreToolUse` フックとして実装し、`Write` / `Edit` / `NotebookEdit` に加えて **`Bash` にも**
掛けています。設計上の要点は 4 点です。

- **`Bash` を対象に含める。** ファイルツールだけを見るフックは
  `cat > local.properties <<EOF` で迂回できます。ヒアドキュメント、リダイレクト、`dd of=` を
  解釈しない対象範囲は実効性を持ちません。
- **相対パスも照合する。** 絶対パスのみの照合では素通りします。
- **読み取りも止める。** `cat local.properties` はシークレットを新たに作りませんが、その内容を
  会話ログへ複製します。開示という点では書き込みと同じです。
- **失敗時は拒否側に倒す。** 入力が解釈できない、`python3` が無い、スクリプトが無い —
  いずれも block です。エラー時に allow する統制は、信頼されるぶん無いよりも危険です。

判定は毎回の `Bash` 呼び出しで走るため、偽陰性はシークレットの流出、偽陽性はエージェントが
自身のリポジトリで作業できなくなることを意味します。したがって両方向の自己テストを置いています。

```bash
python3 .claude/hooks/guard_secrets_test.py     # 49 件、block と allow の両方向
```

## 2. 作業の進め方

1. **計画を先に固める。** 実装に入る前に、19 の PR に分割した実装計画を書き、
   実装者が推測しうるパラメータ（`per_page`、デバウンス、キャッシュ TTL、ブレークポイント、
   タイムアウト、シード色…）をすべて表に固定しました。「決定性の契約」と呼んでいて、
   ここの値を変えることは ADR であって好みではありません。なお計画そのものは作業用
   ドキュメントとして版管理外に置いています。固定した値は `gradle/libs.versions.toml` と
   `docs/adr/` に残っており、そちらが committed な正本です。
2. **1 PR = 1 つの作業単位。** ブランチを切り、Conventional Commits で積み、CI と
   CodeRabbit を通してからマージします。
3. **TDD。** 各 PR はまずテストシナリオの一覧を書き、1 項目ずつ失敗するテストに変えます。
   1 コミット = 1 つの green なサイクルで、テストと実装を別コミットに分けません
   （分けると赤いコミットが履歴に残り、bisect が壊れます）。
4. **リファクタ工程を明示的に回す。** green の窓の中で、振る舞いを変えない整理だけを行います。
5. **PR を開く前に自己レビュー。** 正しさのレビューと、ネットワーク / 認証 / シークレット /
   ビルドバリアントに触れる PR ではセキュリティレビューを別途走らせています。

## 3. AI が間違え、ゲートが捕まえたもの

実際に発生した失敗を記録します。いずれも「AI が生成したことに起因する」よりも「未検証の前提を
信頼したことに起因する」種類のものであり、対策はすべて仕組み側に実装しています。

### 3-1. 全ゲートが緑のまま、Android で起動即クラッシュ

`main` の `7fc5cd8` は、Android で最初の画面を描けませんでした。

```
MissingResourceException: Missing resource with path:
composeResources/…core.designsystem.generated.resources/values/strings.commonMain.cvr
```

ktlint も detekt も Android Lint も全テストスイートも `assembleDebug` も緑でした。
Desktop と iOS は無事だったので、Android で文字列を読む PR が来るまで生き延びていました。

原因は AGP 9 の `com.android.kotlin.multiplatform.library` プラグインに assets パイプラインが
無いことで、Compose Resources は Android では assets からしか読まれません。

**対応:** CI が検証していたのは「ビルドが通ること」のみでした。成果物の内容を検査するタスク
（`verifyProdReleaseComposeResources`）を `check` に接続し、リソースバンドルを含まない APK が
green にならないようにしています。[ADR-0010](adr/0010-package-compose-resources-from-the-application-module.md)

### 3-2. もっともらしい設定で CI が 5 倍遅くなった

Kotlin/Native のリリースリンクがデフォルトヒープを使い切ったため、`gradle.properties` に
`kotlin.native.jvmArgs=-Xmx6g` を追加しました。設定としては妥当に見える変更です。

ただしこのプロパティは**すべての** native コンパイルに適用されます。CI ランナーの総メモリは
約 7 GB のため、あらゆるリンクがスワップに落ちました。計測値は
`linkDebugTestIosSimulatorArm64` が 7.5 分 → 33 分、macOS のジョブ全体が 14 分 → 70 分超です。
**エラーは一切出力されませんでした。** コンパイルではなくページングが行われていたためです。

**対応:** 計測を伴わない性能設定は導入しない方針としました。ヒープ設定は必要な 1 タスクに
実行時のみ渡す形へ変更し、`gradle.properties` には当該設定を記述しない理由を 15 行の
コメントとして残しています。

### 3-3. 計画に書かれた「既知の事実」が 2 件とも誤っていた

実装計画は `lifecycle-viewmodel-navigation3` を 2.11.0 ではなく 2.10.0 に固定し、
「バージョンのずれを PR1 で確認せよ」というリスクとして記録していました。
公開されている Maven メタデータを実際に引くと、**ずれは存在しませんでした**。
同じ確認で Coil の固定値が 1 パッチ古いことも分かりました。

**対応:** AI が生成した「検証済み」の記述も検証対象とする方針としました。以後、固定バージョンは
公開メタデータへの照合を経てから確定する運用です。[ADR-0002](adr/0002-resolve-pinned-versions-against-published-metadata.md)

### 3-4. 予想が外れた側の例

計画は detekt が Kotlin 2.4.10 で動かないと予想し、フォールバック（ktlint + Android Lint のみ）
まで用意していました。実際に試すと**動きました**（型解決が `commonMain` に届かないという制約付き）。

**対応:** フォールバックの用意自体は妥当ですが、検証前に採用すべきではないという結論です。
2 時間のタイムボックスで実験し、その結果をもって決定する運用としています。
[ADR-0003](adr/0003-lint-gate-ktlint-and-detekt.md)

## 4. AI に委譲しなかったこと

- **Git の履歴。** `git commit` / `git push` / `git merge` / `gh pr create` は 1 度も
  エージェントに実行させていません。エージェントの成果物は「レビュー済みの作業ツリー」と
  「ブランチとコミットの計画」までで、実行は人間です。コミット粒度とブランチ運用は
  評価対象であり、そこは道具に任せる判断ではありません。
- **シークレットの作成と取り扱い。** アップロード鍵、Apple の証明書、プロビジョニング
  プロファイル、Firebase のサービスアカウントはすべて人間が作成し、GitHub Secrets に
  登録しています。これらのファイルは版管理外に置き、AI が読み書きする対象にしていません
  （`cat local.properties` はシークレットを新たに作りませんが、その内容を会話ログへ
  複製するため、読み取りも同様に避ける必要があります）。値はビルド時に注入され、
  ソースにも `gradle.properties` にも現れません。
- **固定バージョンの変更。** 「動かないから 1 つ下げる」を禁止し、ADR + 独立した PR に
  しています。
- **評価項目の範囲。** 30 項目を超える作業は「止まって聞く」対象です。スコープクリープは
  シニアリティではありません。

## 5. AI レビューを CI に組み込む

中「AI レビュー」の項目に対して **CodeRabbit** を全 PR で動かしています
（[ADR-0006](adr/0006-use-coderabbit-for-ai-review.md)）。

設計上の要点は、コミット済みの `.coderabbit.yaml` に `path_instructions` を記述し、
**このプロジェクトの規約をレビュー観点として渡している**ことです。汎用的な Kotlin の助言では、
ここで実際に問題になる欠陥 — レイヤリング違反、握り潰された `CancellationException`、
`subscribers_count` ではなく `watchers_count` にバインドされた詳細画面 — は指摘されません。

設定がリポジトリの中にあるので、レビュー観点そのものが PR のレビュー対象になり、
シークレットも不要です（公開リポジトリでは無料）。

---

## 6. まとめ

AI の活用において実効性があったのは、プロンプトの記述内容ではなく、
**規約を検証可能な形に翻訳し、違反時に必ず失敗する場所へ配置すること**でした。

プロンプトの内容は会話の経過とともに希薄になりますが、失敗するテストは希薄になりません。
